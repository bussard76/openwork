# openwork — Agent Memory

## Status

Konzept — noch nicht implementiert.

---

## Ausgangslage

openwork basiert auf OpenCode, dessen Sessions in SQLite gespeichert werden — aber nur innerhalb einer Session. Der Agent kennt beim nächsten Start nichts mehr: keine Entscheidungen, keine Projekte, keine Präferenzen, keine gelernten Patterns.

Dieses Konzept beschreibt ein persistentes Memory-System, das:

- **über Sessions hinweg** Wissen aufbaut (Entitäten, Relationen, Learnings, Skills)
- **Markdown als Source of Truth** nutzt — Git-versionierbar, ohne Server
- **SQLite als Index** nutzt — FTS5-Suche und Graph-Traversal ohne Vektorstore
- **die Hermes-Learning-Loops** (Nous Research) adaptiert — autonome Skill-Erstellung und Distillation
- dem Nutzer **volle Kontrolle** lässt — alles ist Text, alles ist editierbar

Eine UI-Integration in den openwork Tauri-Client (Memory-Tab, Graph-View, Sidebar-Sektion)
ist bewusst ausgeklammert und wird in einem späteren Schritt konzipiert.

Inspirationen: Hermes Agent (Nous Research), OpenClaw, Zettelkasten-Workflow.
Design-Prinzip: **Markdown = Source of Truth, SQLite = Index + Search, Graph = emergent aus Links.**

---

## Kernidee: Ontologisch verlinkter Knowledge Graph

Das Memory ist kein flacher Text. Es ist ein navigierbarer Graph aus typisierten Entitäten
(Personen, Projekte, Tools, Entscheidungen, Learnings, Skills) und typisierten Relationen.

Drei Ebenen:

1. **Hermes' geschlossener Learning Loop** — Der Agent erstellt Skills aus Erfahrung,
   verbessert sie bei Wiederverwendung, entscheidet selbst was ins Langzeitgedächtnis gehört.
2. **Ontologische Verlinkung** — Wissen wird als Markdown mit Frontmatter + Wikilinks
   codiert. Links zwischen Dateien sind Kanten im Graph.
3. **SQLite als universeller Index** — Ein File, kein Server. FTS5 für Volltextsuche,
   JSON-Funktionen für Attribut-Queries, rekursive CTEs für Graph-Traversal.

## Dateistruktur

Das Memory-System existiert auf zwei Ebenen:

```
~/.local/share/openwork/memory/     ← Globales Memory (nutzerübergreifend, projektunabhängig)
│
├── _ontology/                      ← Geteiltes Schema (gilt für global + alle Projekte)
├── entities/
│   ├── person/
│   ├── tool/
│   ├── concept/
│   ├── learning/                   ← Allgemeine Erkenntnisse
│   └── skill/                      ← Wiederverwendbare Skills
├── distilled/
│   ├── USER.md                     ← Nutzer-Präferenzen — immer geladen
│   └── RULES.md                    ← Globale Verhaltensregeln — immer geladen
└── _index/
    └── graph.db

{workspace-root}/
│
└── .memory/                        ← Projekt-Memory (nur aktiv wenn dieser Workspace offen)
    │
    ├── entities/
    │   ├── project/
    │   ├── decision/
    │   ├── learning/               ← Projektspezifische Erkenntnisse
    │   └── skill/                  ← Projektspezifische Skills (selten)
    │
    ├── episodes/                   ← Session-Logs dieses Projekts
    │   └── YYYY-MM-DD.md
    │
    ├── distilled/
    │   └── MEMORY.md               ← Projektspezifische Fakten — nur bei diesem Workspace geladen
    │
    └── _index/
        └── graph.db
```

**Warum `.memory/` im Workspace:**

- Jeder Workspace (git-Repo) hat sein eigenes Memory — Kontext bleibt projektorientiert
- Globale Nutzer-Präferenzen landen in `distilled/USER.md` und können workspace-übergreifend
  per Symlink oder Copy-on-Promote geteilt werden
- `.memory/` ist in `.gitignore` — lokal per Default, optional im Repo trackbar
- Konsistent mit `.opencode/` — Nutzer kennen dieses Muster bereits

## Entity-Format

Jede Entität ist eine Markdown-Datei mit typisiertem Frontmatter und menschenlesbarem Body.

### Frontmatter (maschinenlesbar)

```yaml
---
type: project # Muss in _ontology/entity-types.md definiert sein
id: tauri-tts-app # Canonical ID (default = Datei-Slug)
status: active
created: 2026-03-15
updated: 2026-04-05
tags: [tauri, ai, voice, tts]

relations:
  - target: sascha-gering
    type: owned_by
  - target: opencode
    type: uses
  - target: elevenlabs
    type: depends_on
  - target: 2026-03-tauri-statt-electron
    type: based_on
    context: "Entscheidung gegen Electron wegen Bundle-Größe"

# Temporal (optional, für Fakten die sich ändern)
valid_from: 2026-03-15
# valid_until:
# superseded_by: tauri-tts-app-v2
---
```

### Body (menschenlesbar)

Freier Markdown-Text mit `[[Wikilinks]]` zu anderen Entitäten.
Wikilinks erzeugen "weiche" Kanten im Graph (Konfidenz 0.7 vs. 1.0 bei Frontmatter-Relationen).

### Zwei Arten von Kanten

| Kantentyp     | Quelle                   | Konfidenz | Beispiel                         |
| ------------- | ------------------------ | --------- | -------------------------------- |
| **Hart**      | Frontmatter `relations:` | 1.0       | `{target: opencode, type: uses}` |
| **Weich**     | `[[Wikilinks]]` im Body  | 0.7       | `[[ElevenLabs]]` im Fließtext    |
| **Inferiert** | Agent bei Distillation   | 0.3       | Kookkurrenz-Pattern aus Episodes |

## Ontologie-Schema

### Entity Types (`_ontology/entity-types.md`)

```
person    — required: [name]           relations: [works_at, collaborates_with, knows]
project   — required: [name, status]   relations: [owned_by, uses, depends_on, based_on]
tool      — required: [name]           relations: [used_by, integrates_with, replaces]
concept   — required: [name, domain]   relations: [related_to, extends, instance_of]
decision  — required: [date, outcome]  relations: [affects, supersedes, revisit_after]
learning  — required: [category]       relations: [applies_to, learned_from, supersedes]
skill     — required: [name, trigger]  relations: [uses_tool, learned_from, created_by]
```

### Relation Types (`_ontology/relation-types.md`)

Alle Relationen sind typisiert. Inverse Paare werden vom Index automatisch generiert:
`owns ↔ owned_by`, `uses ↔ used_by`, `depends_on ↔ dependency_of`, etc.

### Distillation Rules

Wann wird ein Learning zu einem permanenten Fakt in `distilled/MEMORY.md` oder `RULES.md`?

- `recurrence >= 3` — mindestens 3x in Episodes aufgetaucht
- In >= 2 verschiedenen Entity-Kontexten gesehen
- Innerhalb eines 30-Tage-Fensters
- Nicht von einem neueren Learning widersprochen

## SQLite Index

`_index/graph.db` ist ein generierter Index — jederzeit aus den Markdown-Files neu aufbaubar.
Bei Corruption: Rebuild via Tool oder Command. Kein Datenverlust möglich.

### Tabellen

```sql
-- Knoten
CREATE TABLE entities (
    id TEXT PRIMARY KEY,
    type TEXT NOT NULL,
    file_path TEXT NOT NULL,
    title TEXT,
    status TEXT,
    created TEXT,
    updated TEXT,
    valid_from TEXT,
    valid_until TEXT,
    superseded_by TEXT,
    tags TEXT,            -- JSON Array
    attributes TEXT,      -- JSON Object (alle weiteren Frontmatter-Felder)
    body_text TEXT        -- Volltext für FTS
);

CREATE VIRTUAL TABLE entities_fts USING fts5(
    id, title, tags, body_text,
    content=entities, content_rowid=rowid
);

-- Kanten
CREATE TABLE relations (
    source_id TEXT NOT NULL,
    target_id TEXT NOT NULL,
    type TEXT NOT NULL,
    context TEXT,
    origin TEXT DEFAULT 'frontmatter',  -- 'frontmatter' | 'wikilink' | 'inferred'
    confidence REAL DEFAULT 1.0,
    UNIQUE(source_id, target_id, type)
);

CREATE INDEX idx_rel_source ON relations(source_id);
CREATE INDEX idx_rel_target ON relations(target_id);

-- Episodes
CREATE TABLE episodes (
    date TEXT PRIMARY KEY,
    file_path TEXT NOT NULL,
    body_text TEXT,
    entities_mentioned TEXT,     -- JSON Array
    learnings_extracted TEXT     -- JSON Array
);

CREATE VIRTUAL TABLE episodes_fts USING fts5(
    date, body_text, content=episodes, content_rowid=rowid
);

-- Skill-Nutzungs-Tracking
CREATE TABLE skill_usage (
    skill_id TEXT NOT NULL,
    used_at TEXT NOT NULL,
    outcome TEXT,                -- 'success' | 'partial' | 'failed'
    improvement_made INTEGER DEFAULT 0,
    notes TEXT
);
```

### Beispiel-Queries

```sql
-- Nachbarn eines Knotens (1-Hop)
SELECT r.type, r.target_id, e.type, e.title
FROM relations r JOIN entities e ON e.id = r.target_id
WHERE r.source_id = 'tauri-tts-app' ORDER BY r.confidence DESC;

-- Volltextsuche
SELECT id, title, rank FROM entities_fts
WHERE entities_fts MATCH 'websocket latency' ORDER BY rank LIMIT 10;

-- Promotion-Kandidaten (recurrence >= 3, <= 30 Tage)
SELECT id, title, json_extract(attributes, '$.recurrence') as n
FROM entities WHERE type = 'learning'
AND json_extract(attributes, '$.status') = 'pending'
AND CAST(json_extract(attributes, '$.recurrence') AS INTEGER) >= 3
AND julianday(json_extract(attributes, '$.last_seen'))
    - julianday(json_extract(attributes, '$.first_seen')) <= 30;

-- Skills nach Effektivität
SELECT id, title,
    json_extract(attributes, '$.times_used') as uses,
    json_extract(attributes, '$.effectiveness_score') as score
FROM entities WHERE type = 'skill'
ORDER BY CAST(json_extract(attributes, '$.effectiveness_score') AS REAL) DESC;
```

## Learning Loops

### Micro-Loop — nach jeder Agent-Interaktion (still, < 100 Tokens)

```
1. Entity-Check    — Neue Person/Tool/Konzept erwähnt ohne Datei? → entities/{type}/{slug}.md anlegen
2. Relation-Check  — Neue Verbindung zwischen bekannten Entitäten sichtbar? → Frontmatter ergänzen
3. Correction-Check— Nutzer hat etwas korrigiert? → entities/learning/LRN-{NNN}-{slug}.md erstellen
4. Skill-Kandidat  — Task war komplex (≥5 Tool-Calls)? → Episode markieren, Skill-Loop triggern
```

### Skill-Loop — nach komplexem Task (Hermes-Pattern)

```
1. EVALUATE  — War das Ergebnis erfolgreich?
2. EXTRACT   — Prozedur in Schritten dokumentieren
3. CREATE    — entities/skill/{slug}.md mit:
               ## Trigger, ## Procedure, ## Pitfalls, ## Verification
4. LINK      — Relationen zu verwendeten Tools + relevanten Concepts
5. INDEX     — SQLite inkrementell aktualisieren

BEI WIEDERVERWENDUNG:
1. LOAD      — Skill per FTS5 oder Graph-Traversal finden
2. APPLY     — Prozedur befolgen
3. EVALUATE  — Besser oder schlechter als erwartet?
4. IMPROVE   — Bei besserem Ansatz: version++, changelog++, score anpassen
```

### Distillation-Loop — periodisch (alle 2–3 Tage oder on-demand)

```
1. SCAN      — Episodes der letzten 7 Tage lesen
2. EXTRACT   — Wiederkehrende Muster identifizieren
3. PROMOTE   — Learnings die Kriterien erfüllen → distilled/MEMORY.md oder RULES.md
4. PRUNE     — Entities die >90 Tage nicht referenziert wurden als "stale" markieren
5. EVOLVE    — Schema-Evolution prüfen: neue Ad-hoc-Typen → _ontology/evolution-log.md
```

### Reflection-Loop — wöchentlich (optional)

```
1. GRAPH     — Isolierte Cluster, dichte Cluster, zentrale Knoten identifizieren
2. GAPS      — Concepts mit maturity:exploring seit >30 Tagen nicht aktualisiert
               Decisions mit revisit_after in der Vergangenheit
               Skills mit score < 0.5
3. SYNTHESIZE— Querverbindungen zwischen Clustern vorschlagen
4. META      — Hat die Ontologie die richtigen Typen? Sind Distillation-Rules noch passend?
```

## Workspace-Scoping

openwork kennt zwei Workspace-Typen (aus dem UI-Redesign-Konzept):

- **Home-Workspace** — globaler Kontext, immer verfügbar, kein Projektverzeichnis
- **Projekt-Workspace** — an ein Verzeichnis (git-Repo) gebunden, wird im Work-Modus geöffnet

Das Memory-System folgt diesem Muster mit zwei Ebenen:

### Globales Memory (`~/.local/share/openwork/memory/`)

Lebt außerhalb jedes Projekts. Enthält:

- `distilled/USER.md` — Nutzer-Präferenzen, Arbeitsstil, persönliche Regeln
- `distilled/RULES.md` — globale Verhaltensregeln für den Agent
- `entities/person/`, `entities/tool/`, `entities/concept/` — Wissen das projektübergreifend gilt

Wird bei **jeder Session** geladen, unabhängig vom aktiven Workspace.

### Projekt-Memory (`.memory/` im Workspace-Root)

Lebt im Projektverzeichnis. Enthält:

- `distilled/MEMORY.md` — projektspezifische Fakten
- `entities/project/`, `entities/decision/`, `entities/learning/`, `entities/skill/` — Wissen das nur dieses Projekt betrifft
- `episodes/` — Session-Logs dieses Projekts
- `_ontology/` und `_index/` — Schema + Index (teilt Ontologie mit globalem Memory)

Wird nur geladen wenn der aktive Workspace dieses Verzeichnis ist.

### Kombinierte Ladestrategie

```
Session-Start in Projekt-Workspace:

  GLOBAL  ~/.local/share/openwork/memory/distilled/USER.md   → System-Prompt
  GLOBAL  ~/.local/share/openwork/memory/distilled/RULES.md  → System-Prompt
  PROJEKT .memory/distilled/MEMORY.md                        → System-Prompt
  PROJEKT .memory/episodes/today.md      (wenn vorhanden)    → Kontext
  PROJEKT .memory/episodes/yesterday.md (wenn vorhanden)     → Kontext
  GLOBAL  entities/skill/ Übersicht      (Name + Description) → System-Prompt
  PROJEKT entities/skill/ Übersicht      (Name + Description) → System-Prompt

Session-Start im Home-Workspace (Chat-Modus, kein Projekt):

  GLOBAL  USER.md + RULES.md                                 → System-Prompt
  (kein MEMORY.md, kein Episodes-Kontext)
```

Token-Budget: ~2.000–3.500 Tokens gesamt — ca. 1–2 % eines 200k-Fensters.

### Schreiben: Wo landet neues Wissen?

Der Micro-Loop entscheidet anhand des Inhalts:

| Wissenstyp                           | Ziel                                   |
| ------------------------------------ | -------------------------------------- |
| Neue Person / Tool / Konzept         | Globales Memory (`entities/`)          |
| Projekt-Entscheidung, Architektur    | Projekt-Memory (`entities/`)           |
| Learning das Projekt-spezifisch ist  | Projekt-Memory (`entities/learning/`)  |
| Learning das allgemein gilt          | Globales Memory (`entities/learning/`) |
| Skill (wiederverwendbares Verfahren) | Globales Memory (`entities/skill/`)    |
| Nutzer-Präferenz                     | Globales Memory (`distilled/USER.md`)  |
| Projektspezifischer Fakt             | Projekt-Memory (`distilled/MEMORY.md`) |

Im Zweifel gilt: **Projekt-Memory** — lieber zu eng als zu breit. Globale Promotion
erfolgt explizit im Distillation-Loop.

## Memory-Einstellung

Das Memory-System kann global und pro Workspace ein- und ausgeschaltet werden.
Die Einstellung folgt dem gleichen Muster wie `openwork.theme` — gespeichert in `opencode.json`.

### Globale Einstellung

```jsonc
// ~/.config/opencode/opencode.json
"openwork": {
  "memory": {
    "enabled": true   // true = Memory aktiv (Standard), false = vollständig deaktiviert
  }
}
```

Ist `enabled: false`, passiert beim Session-Start nichts — kein Inject, kein Micro-Loop,
kein Index-Update. Das `.memory/`-Verzeichnis bleibt erhalten, wird aber ignoriert.

### Workspace-Override

Ein einzelner Workspace kann das globale Setting überschreiben. Dazu wird
`openwork.memory.enabled` in einer `.opencode/config.json` im Workspace-Root gesetzt:

```jsonc
// {workspace-root}/.opencode/config.json
"openwork": {
  "memory": {
    "enabled": false   // deaktiviert Memory nur für diesen Workspace
  }
}
```

Damit ist z. B. möglich: Memory global aktiv, aber für ein bestimmtes Kundenprojekt
(Datenschutz, vertrauliche Inhalte) explizit deaktiviert — und umgekehrt.

### Auswertungsreihenfolge

```
1. Workspace-Override (.opencode/config.json im Workspace-Root) — höchste Priorität
2. Globale Einstellung (~/.config/opencode/opencode.json)
3. Default: enabled = true
```

### Was genau wird deaktiviert

| Funktion                            | Bei `enabled: false` |
| ----------------------------------- | -------------------- |
| Memory-Injection beim Session-Start | Nicht ausgeführt     |
| Micro-Loop (Schreiben ins Memory)   | Nicht ausgeführt     |
| Distillation-Loop                   | Nicht ausgeführt     |
| FTS5-Suche / Graph-Traversal        | Nicht ausgeführt     |
| `/memory-*` Commands                | Geben Hinweis zurück |
| `.memory/`-Verzeichnis              | Bleibt erhalten      |

Das Verzeichnis wird nie automatisch gelöscht — Nutzer entscheidet bewusst ob er
gespeichertes Wissen entfernen möchte.

## Session-Lifecycle

### Session-Start (Context Assembly)

Der Inject wird vom **openwork-Core automatisch** beim Session-Start ausgeführt —
außerhalb des Agent-Kontexts, bevor der Agent überhaupt startet. Der Agent sieht
`USER.md`, `RULES.md`, `MEMORY.md` bereits im System-Prompt wenn er die erste
Nachricht erhält. Er muss sie nicht selbst lesen.

Reihenfolge beim Aufbau des System-Prompts (von oben nach unten, festes Budget):

```
1. Globales USER.md      (~500 Tokens)   — immer
2. Globales RULES.md     (~300 Tokens)   — immer
3. Projekt MEMORY.md     (~800 Tokens)   — nur bei Projekt-Workspace
4. Skill-Übersicht       (~50 T/Skill)   — global + projekt, nur Name + Trigger
5. episodes/today.md     (variabel)      — nur bei Projekt-Workspace, wenn vorhanden
6. episodes/yesterday.md (variabel, max ~300 T) — nur bei Projekt-Workspace, wenn vorhanden

Gesamt-Budget: ~2.000–3.500 Tokens
```

Überschreitet ein File das Budget, wird es **hinten abgeschnitten** — nie vorne.
Überschreitet das Gesamt-Budget den Schwellwert, fallen episodes als erstes weg,
dann MEMORY.md (auf die ersten 400 Tokens gekürzt), USER.md und RULES.md niemals.

### Während der Session (Pull-Mechanismus)

Memory wird mid-session **nicht automatisch nachgeladen**. Der Agent zieht aktiv nach
wenn er es braucht — gesteuert durch einen kurzen Hinweis im System-Prompt.

#### Implementierung: Bash-Scripts, kein eigenes Tool-Schema

Die Memory-Abfrage läuft **nicht** als registriertes opencode-Tool und **nicht** als MCP-Server.
Beide Optionen hätten zu viel Token-Overhead: Tool-Schemas erscheinen bei jeder Session
vollständig im System-Prompt, MCP-Prozesse benötigen zusätzlich Verbindungs-Overhead.

Stattdessen: Der Agent nutzt das bereits vorhandene `bash`-Tool und ruft einfache
Bun-Scripts auf. Das kostet keine zusätzlichen Schema-Tokens — nur ~5 Zeilen Hinweis
in `distilled/RULES.md`:

```markdown
## Memory-Zugriff

Persistentes Wissen liegt in .memory/. Nutze diese Scripts bei Bedarf:

- `bun .memory/scripts/search.ts "<query>"` → FTS5-Suche, JSON-Output
- `bun .memory/scripts/graph.ts "<entity-id>"`→ 1-Hop-Nachbarn, JSON-Output
- `bun .memory/scripts/get.ts "<entity-id>"` → Vollinhalt einer Entity
```

Der Agent entscheidet selbst wann er sucht — kein automatisches Retrieval bei jeder
Nachricht. Das verhindert unkontrolliertes Token-Wachstum.

#### Wann sucht der Agent typischerweise?

- Nutzer erwähnt ein Projekt / eine Person / ein Tool das der Agent nicht kennt
- Agent braucht den Vollinhalt eines Skills den er in der Übersicht gesehen hat
- Agent merkt dass eine frühere Entscheidung relevant ist (`/memory-graph`)
- Nutzer fragt explizit nach etwas aus dem Memory

### Session-Ende

```
1. Episode finalisieren  → .memory/episodes/YYYY-MM-DD.md (Projekt)
2. Pending Learnings prüfen
3. SQLite Index inkrementell aktualisieren (Projekt + Global)
4. Optional: Distillation-Loop wenn >3 Tage seit letztem Lauf
```

## opencode Custom Agent

Ein dedizierter Memory-Agent übernimmt Maintenance-Aufgaben:

```markdown
# .opencode/agents/memory.md

Du bist der Memory-Agent für openwork. Du pflegst und entwickelst das
Wissenssystem in .memory/entities/ weiter.

Kein eigenes Tool-Schema — du nutzt ausschließlich das vorhandene `bash`-Tool
mit Bun-Scripts (`bun .memory/scripts/...`). Die Kurzformen index-build,
index-query, distill, ontology-check sind Bezeichnungen für diese Script-Aufrufe,
keine registrierten opencode-Tools.

Regeln:

- Lies \_ontology/entity-types.md bevor du neue Entitäten erstellst
- Erstelle nie einen neuen Entity-Type ohne Eintrag in evolution-log.md
- Halte MEMORY.md unter 2.200 Zeichen (~800 Tokens)
- Halte USER.md unter 1.375 Zeichen (~500 Tokens)
- Setze Learning-Status nie ohne Promotion-Kriterien-Check auf "promoted"
```

## Index-Build Pipeline

### Full Rebuild

```
index-build --full

1. Alle .md Files in entities/ und episodes/ parsen
2. Frontmatter (YAML) und Wikilinks extrahieren
3. SQLite DROP + CREATE + INSERT
4. Inverse Relationen generieren (gemäß relation-types.md)
5. FTS5-Index rebuilden
6. Integritätsprüfung:
   - Broken Links (target_id existiert nicht)
   - Orphan Entities (keine Relationen)
   - Schema-Violations (type nicht in entity-types.md)
7. Report ausgeben
```

### Inkrementelles Update

```
index-build --incremental

1. mtime-basiert: Welche .md Files haben sich geändert?
2. Nur geänderte Files re-parsen
3. Alte Einträge löschen, neue einfügen
4. FTS5 aktualisieren
Ziel: < 100 ms für einzelne Datei-Änderungen
```

## Beispiel: Kompletter Learning-Lifecycle

### Schritt 1 — Episode entsteht (Session-Protokoll)

```markdown
# episodes/2026-04-05.md

## Session: Tauri TTS App

Debugging der [[ElevenLabs]] WebSocket-Verbindung.
Problem: Streaming-Latenz von 2s beim ersten Chunk.

Lösung: Connection Pre-warming beim App-Start statt lazy init.
Latenz von 2s auf 200ms reduziert.
```

### Schritt 2 — Micro-Loop extrahiert Learning

```yaml
# entities/learning/LRN-051-websocket-prewarm.md
---
type: learning
id: LRN-051-websocket-prewarm
category: best_practice
status: pending
recurrence: 1
first_seen: 2026-04-05
last_seen: 2026-04-05
relations:
  - target: tauri-tts-app
    type: applies_to
  - target: elevenlabs
    type: applies_to
---
WebSocket-Verbindungen zu Streaming-APIs sollten beim App-Start
vorgewärmt werden, nicht lazy beim ersten Request.
Reduktion: 2s → 200ms First-Chunk-Latency.
```

### Schritt 3 — Recurrence steigt

In zwei weiteren Projekten taucht dasselbe Pattern auf.
Agent setzt `recurrence: 3`, `last_seen` aktuell.

### Schritt 4 — Promotion

Distillation-Loop erkennt: recurrence=3, 3 Kontexte, < 30 Tage.

```markdown
# Ergänzung in distilled/RULES.md:

- WebSocket/Streaming-Verbindungen immer beim App-Start pre-warmen.
  Connection-Pool bei mehreren Endpoints.
```

Learning-Status → `promoted`.

  - target: LRN-051-websocket-prewarm
    type: learned_from

## Procedure
1. Alle WebSocket-Endpoints im Projekt identifizieren
2. Connection-Manager mit Pre-Warming beim App-Start implementieren
3. Reconnect-Logic mit exponential Backoff hinzufügen
4. First-Chunk-Latency messen (vorher/nachher)

## Pitfalls

- Memory-Leak: Connections bei Unmount / Navigation schließen

## Verification

- Reconnect funktioniert nach Network-Interrupt

## Design-Entscheidungen

### Warum Markdown als Source of Truth (nicht SQLite)?

Git-versionierbar, diffbar, mergebar. Menschenlesbar ohne Tools. Portabel.
SQLite ist generierter Index — bei Corruption: Rebuild aus den .md Files.

### Warum SQLite als Index (nicht pure grep)?

FTS5 ist mächtiger als grep. JSON-Funktionen erlauben Attribut-Queries.
Rekursive CTEs ermöglichen Graph-Traversal. Ein File, kein Server.

### Warum kein Embedding/Vektorstore?

Braucht lokales Embedding-Modell oder API-Calls. FTS5 + Graph-Traversal
deckt 80 %+ der Suchfälle ab. Kann in Phase 5 nachgerüstet werden
(sqlite-vec Extension). Hermes zeigt: FTS5 reicht für produktiven Alltag.

### Warum `.memory/` und nicht direkt im Workspace-Root?

Klare Abgrenzung vom Projekt-Code. Konsistent mit `.opencode/`.
In `.gitignore` per Default — Nutzer entscheidet bewusst ob Memory getrackt wird.
